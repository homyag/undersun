# TASK + WORKFLOW: интеграция AREALISTING API

## 1. Статус и контекст

- Ветка: `feature/arealisting-api-properties`
- Документация API: <https://arealisting.com/api/v1/docs#description/introduction>
- Версия API из документации: `1.1.0`
- Ручная проверка `GET /projects` и `GET /units`: выполнена `2026-09-01`
- Base URL: `https://arealisting.com/api/v1`
- Ключ хранится только в `.env`:

  ```dotenv
  AREALISTING_API_KEY=
  ```

- Авторизация каждого запроса:

  ```http
  Authorization: Bearer <AREALISTING_API_KEY>
  ```

Этот документ одновременно является постановкой задачи (`TASK_AREALISTING`) и рабочим процессом реализации (`WORKFLOW`). По мере разработки чек-листы и принятые решения необходимо обновлять здесь.

### 1.2 Что фактически обновляется в Undersun сейчас

Отчёт о ценах: каждый запуск сохраняет в `SyncRun.summary.price_updates` старые и новые цены THB/USD/RUB, время проверки, карточку и результат `updated/unchanged/skipped`. На странице подбора выбранного комплекса показывается последний сохранённый отчёт с понятными статусами и конкретной причиной пропуска (например, нет доступных выбранных предложений или цена защищена). Это снимок проверки, а не текущая цена после последующих ручных правок. Отчёт доступен после перезагрузки страницы; миграция для него не требуется.

Цена связанного `Property` обновляется автоматически после успешного прохода синхронизации проектов/юнитов/удалений (не в dry-run), а также ежедневной production-командой `update_arealisting_prices`. Берётся минимальная положительная цена среди AVAILABLE, не удалённых, явно связанных units; посторонние и новые несопоставленные units комплекса не участвуют. Если с карточкой связан один unit, используется цена именно этого unit. Через `CurrencyService` рассчитываются THB/USD/RUB и обновляются вместе. При отсутствии курса, доступных units, некорректной цене, отключённой синхронизации unit или блокировке любого ценового поля все прежние цены сохраняются, предупреждение записывается в `ListingGroup.validation_errors`. Статус и активность карточки не меняются. Само сохранение связи цену немедленно не меняет: она изменится после следующего успешного получения inventory, в том числе по ежедневному расписанию в 00:30 `Asia/Bangkok`.

Проверено по `apps/arealisting/services/matching.py`, `services/sync.py`, `services/pricing.py` и команде `update_arealisting_prices` на 2026-09-07. Получение данных AREALISTING и изменение публичной карточки — разные операции.

| Поле карточки Undersun | Источник | Условие переноса |
|---|---|---|
| `complex_name_ru` — название комплекса RU | `ArealistingProject.name_ru` | Непустое значение, поле выбрано администратором |
| `complex_name_en` — название комплекса EN | `ArealistingProject.name_en` | Непустое значение, поле выбрано администратором |
| `bedrooms` — спальни | `ArealistingUnit.bedrooms` | Одинаковое непустое значение у всех выбранных units, поле выбрано |
| `floor` — этаж | `ArealistingUnit.floor` | Одинаковое непустое значение у всех выбранных units, поле выбрано |
| `area_total` — общая площадь | `ArealistingUnit.internal_area_sqm` | Одинаковое непустое значение у всех выбранных units, поле выбрано |

- Это полный текущий список характеристик, переносимых из AREALISTING в существующую карточку. Все изменения требуют подтверждения на экране сравнения; отдельные поля можно исключить для каждой карточки.
- Если у выбранных units разные этажи, площади или число спален, соответствующее поле не предлагается к переносу. Например, связь с квартирами на нескольких этажах не меняет этаж карточки.
- Допуск площади до 1 м² применяется только к поиску кандидатов. При подтверждённом переносе сохраняется фактическая площадь источника, без округления и усреднения.
- Заблокированные поля (`locked_fields`) не перезаписываются. Проверка конфликтов или ошибки одного элемента откатывают весь пакет.
- Если поля не выбраны, сохраняется только связь с проектом и units, без изменения данных `Property`.
- Планы оплаты, maintenance fee, sinking fund и прочие комиссии остаются только в source-моделях и не переносятся в `Property` по решению клиента от 2026-09-13.
- Фотографии импортируются только отдельным явным действием. Маркетинговая gallery проекта становится основной галереей, материалы связанных units классифицируются по имени файла, а изображения `FLOOR_PLAN`/`MASTER_PLAN` попадают в отдельный блок планировок. PDF и другие документы не создают `PropertyImage`.
- ID, URL/slug, SEO-настройки, тайские переводы, продвижение, контакты и счётчик просмотров не изменяются этим переносом. `Property.is_active` может измениться только как отдельное явно подтверждённое действие администратора с проверкой исходного значения и `locked_fields`.
- **После успешной синхронизации автоматически обновляются только цены продажи.** Для переноса пяти характеристик из таблицы администратор снова проверяет и подтверждает изменения.
- SOLD, deletion и отсутствие доступных units сейчас не меняют статус или активность существующей карточки Undersun автоматически. Соответствующая политика остаётся отдельной задачей.

Последующие разделы с более широким mapping и автоматическими price/status updates описывают целевое развитие, а не уже работающие возможности.

### 1.3 Рабочие сценарии администратора

#### Кнопка «Обновление карточек из AREALISTING»

Сценарий:

- выбирается проект AREALISTING;
- загружаются юниты выбранного проекта;
- юниты сопоставляются с существующими объектами Undersun;
- администратор проверяет предложенные изменения и сохраняет связи;
- после сопоставления цена связанных объектов обновляется автоматически каждый день в 00:30 по времени Пхукета.

#### Кнопка «Объекты Undersun без связи»

Сценарий:

- выбирается несопоставленная карточка Undersun во вкладке «Нужно разобрать»;
- по названию комплекса или застройщика находится проект AREALISTING;
- при необходимости загружаются юниты найденного проекта;
- для выбранной карточки подбирается один или несколько соответствующих юнитов;
- администратор проверяет предложенные изменения и сохраняет связь;
- если подходящего проекта или юнита нет, карточка отмечается «Ведём вручную» и исчезает из очереди «Нужно разобрать»;
- отметку можно снять действием «Вернуть в подбор»;
- после сохранения связи отметка ручного ведения снимается автоматически, а цена карточки обновляется по ежедневному расписанию.

Правило цены одинаково для обоих сценариев: при одном выбранном AVAILABLE unit переносится его цена; при нескольких выбранных AVAILABLE units используется минимальная цена. Значения сохраняются в THB, USD и RUB. Если выбранные units проданы или недоступны, синхронизация отключена либо цена защищена, прежняя цена карточки сохраняется, а причина записывается в отчёт.

## 2. Цель

Реализовать интерфейс Django Admin для получения данных AREALISTING, сопоставления их с существующими карточками Undersun Estate и контролируемого обогащения этих карточек. Сохранение текущего каталога — основной сценарий; создание новых карточек — отдельное явное действие администратора.

### 2.1 Согласованный приоритет от 2026-09-05

- Получение проектов и units сохраняет данные только в локальных source-моделях. Само получение данных не создаёт и не публикует `Property`.
- Администратор выбирает существующий `Property`, связывает его с проектом AREALISTING и явно выбирает связанные units. Проект предоставляет общие сведения о комплексе; units — сведения о конкретном предложении.
- Существующая карточка сохраняет свой ID, URL и локальные данные. Обогащение применяется к ней, без создания замены или дубля. Набор обновляемых полей требует отдельной настройки; связывание само по себе не разрешает перезапись всех полей.
- Units без подтверждённой связи остаются доступны только в разделе AREALISTING админки. Они не участвуют в публичной выдаче, фильтрах, счётчиках, диапазонах цен, карте или sitemap Undersun.
- Привязка проекта не означает автоматического включения всех его units: новые units после синхронизации также требуют отдельного выбора администратора, прежде чем влиять на публичное предложение.
- Для отсутствующего в Undersun предложения администратор отдельно выбирает «Создать карточку Undersun». Создаётся неактивный черновик; публикация — отдельное действие после проверки.
- Full/delta sync и будущий `--publish` не должны обходить явный выбор администратора или автоматически расширять каталог за счёт несопоставленных units.

Эти правила уточняют все последующие разделы о группировке, импорте и публикации. Конкретные правила агрегации цены/статуса нескольких units и обработки SOLD остаются открытыми.

Интеграция должна:

- получать проекты, юниты, планы оплаты и удаления;
- сохранять каждый внешний unit, обогащать подтверждённые существующие `Property` и создавать новые только по отдельному указанию администратора;
- сохранять связь с внешними `external_id`;
- поддерживать полную и инкрементальную синхронизацию;
- скачивать изображения в локальное media-хранилище;
- не удалять физически опубликованные объекты;
- не затирать локальные SEO-настройки, служебные поля и ручные настройки продвижения;
- допускать безопасную проверку через `--dry-run` до любых изменений БД;
- предоставлять администратору локальную очередь импорта без ручного ввода API-параметров;
- не делать публичные страницы зависимыми от доступности AREALISTING API.

## 3. Что не входит в первый этап

- Запросы к AREALISTING непосредственно во время открытия страниц сайта.
- Отправка изменений из Undersun Estate обратно в AREALISTING.
- Автоматическая публикация всех полученных объектов без проверки маппинга географии и данных.
- Новый публичный интерфейс для планов оплаты и документов проекта.
- Автоматическое создание тайских переводов без отдельного контролируемого процесса.

## 4. Возможности API

API является read-only источником для партнёрской синхронизации.

| Endpoint | Назначение |
|---|---|
| `GET /projects` | Опубликованные проекты, доступные партнёру |
| `GET /units` | Юниты доступных проектов |
| `GET /payment-plans` | Планы оплаты проектов |
| `GET /deletions` | Физически удалённые сущности для delta-sync |

На `2026-09-01` отдельный `/locations` ещё не опубликован в OpenAPI `1.1.0`. География доступна только как вложенный `project.districts`. Команда AREALISTING анонсировала новый endpoint; реализацию его клиента нужно начинать после появления проверяемого контракта и примера ответа.

List endpoints поддерживают:

- `updated_since` — изменения с указанного времени;
- `limit` — от 1 до 500, значение по умолчанию 100;
- `cursor` — непрозрачный курсор из `meta.next_cursor`;
- `ids` — список `external_id` через запятую;
- `project_id` — фильтр юнитов и планов оплаты по проектам.

Ответ содержит:

```json
{
  "data": [],
  "meta": {
    "next_cursor": null,
    "has_more": false
  }
}
```

Важно: снятие проекта из доступного партнёру набора не появляется в `/deletions`. Поэтому одной delta-синхронизации недостаточно — периодически нужна полная сверка доступных ID.

## 5. Архитектура

AREALISTING не должен использоваться как runtime backend каталога.

```text
AREALISTING API
      |
      v
ArealistingClient
      |
      v
Локальные source-модели
Project / Unit / PaymentPlan / Asset
      |
      v
Publication grouping + Mapper / Projector
      |
      v
Property / Developer / PropertyFeature / PropertyImage
      |
      v
Публичный каталог Undersun Estate
```

Синхронизация делится на три логических этапа:

1. Получить и сохранить состояние внешнего источника.
2. Сгруппировать юниты по выбранной продуктовой модели: проект, планировка или отдельный юнит.
3. Проверить и преобразовать выбранные группы в модели публичного каталога.

Это позволяет повторно выполнить маппинг без повторного обращения к API и проверить данные до публикации.

Администратор не должен вручную вводить endpoint, cursor, `project_id` или `external_id`. Интеграция сама синхронизирует доступный feed, а Django Admin показывает локальную очередь проектов и юнитов с понятными действиями.

## 8. Модели интеграции

### 8.1 `ArealistingProject`

Минимальные поля:

- `external_id` — уникальный ID источника;
- `name_ru`, `name_en`;
- `developer_name`;
- `project_type`;
- `construction_status`;
- `completion_date`;
- `latitude`, `longitude`;
- ownership, maintenance fee и sinking fund;
- `raw_payload` — исходный JSON для диагностики и повторного маппинга;
- `remote_updated_at`;
- `synced_at`.

### 8.2 `ArealistingUnit`

Минимальные поля:

- `external_id` — уникальный ID источника;
- `project` — FK на `ArealistingProject`;
- nullable FK на выбранную публикационную группу;
- `unit_number`, bedrooms, bathrooms, floor и площади;
- исходные цена и валюта;
- внешний статус доступности;
- `raw_payload`;
- `remote_updated_at`;
- `synced_at`;
- `sync_enabled` — разрешено ли обновлять локальный объект;
- последняя ошибка маппинга.

Каждый внешний unit всегда хранится отдельно, даже если он не публикуется или объединён с другими units в одну карточку.

### 8.3 `ArealistingListingGroup`

Промежуточная сущность между source units и публичным `Property`:

- `project` — FK на `ArealistingProject`;
- `property` — nullable `OneToOneField` на `Property`;
- `grouping_mode` — `PROJECT`, `LAYOUT` или `UNIT`;
- обратная FK-связь с выбранными `ArealistingUnit`;
- название группы или планировки;
- минимальная и максимальная цена;
- минимальная и максимальная площадь;
- количество доступных units;
- флаг готовности к публикации;
- `locked_fields` — поля связанного `Property`, защищённые от source updates;
- ошибки и предупреждения валидации.

Эта модель нужна, потому что фактический feed содержит много похожих units одного проекта. Пока API не отдаёт отдельный `layout_id`, группировка по планировкам не должна выполняться только по имени файла или приблизительно одинаковой площади.

### 8.4 `ArealistingPaymentPlan`

- `external_id`;
- FK на `ArealistingProject`;
- название и описание;
- структурированные этапы либо `JSONField` для `items`;
- `raw_payload`;
- `remote_updated_at`;
- `synced_at`.

### 8.5 `ArealistingLocationMapping`

Нужен явный маппинг внешней географии:

- `external_id` географической сущности AREALISTING;
- отображаемое имя источника;
- внешний тип и parent ID, когда они появятся в API;
- FK на локальный `District`;
- nullable FK на локальный `Location`;
- режим `DISTRICT`, `LOCATION`, `IGNORE`;
- флаг активности/подтверждения.

В API `1.1.0` поле `project.districts` фактически содержит в одном плоском массиве географические сущности разных уровней. В проверенном проекте это `Nai Yang`, `Sakhu` и `Amphoe Thalang`. Неизвестные сущности нельзя автоматически создавать и сразу публиковать: API не передаёт тип уровня, parent ID и основной элемент, а Undersun использует двухуровневую структуру `District -> Location`.

### 8.6 `ArealistingAsset`

- nullable FK на `ArealistingProject` или `ArealistingUnit`;
- nullable `OneToOneField` на `PropertyImage` для визуальных assets;
- nullable локальный `FileField` для документов и презентаций;
- исходный URL;
- тип `PROJECT_GALLERY`, `UNIT_GALLERY`, `FLOOR_PLAN`, `PRESENTATION`, `OTHER`;
- позиция в галерее;
- checksum, если его возможно рассчитать;
- время успешной загрузки;
- последняя ошибка загрузки.

### 8.7 `ArealistingSyncState` и `ArealistingSyncRun`

Состояние должно хранить:

- ресурс или единый feed;
- `last_successful_sync_at`;
- начало текущего запуска;
- статус `running/success/failed`;
- счётчики created/updated/skipped/deactivated/errors;
- безопасный текст последней ошибки без токена.

Историю запусков полезно хранить отдельно, чтобы диагностировать изменения и сбои cron.

## 9. Почему нельзя использовать `legacy_id`

`Property.legacy_id` предназначен для старой Joomla-системы, участвует в существующем поиске и имеет ограничение длины 20 символов.

Связь с AREALISTING должна храниться отдельно. Уникальность обеспечивается по source-модели `ArealistingUnit.external_id`, а не через `legacy_id`.

## 12. Валюты

Базовая валюта проекта — THB, публичный UI работает с THB/USD/RUB. API может вернуть THB, USD, EUR или RUB.

Правила:

1. Всегда сохранять исходные `price` и `currency` в `ArealistingUnit`.
2. Для `Property` получить корректную THB-цену.
3. USD и RUB рассчитывать существующим валютным сервисом.
4. Не публиковать объект с ошибочной или неподтверждённой конвертацией.
5. Отдельно решить поддержку EUR в справочнике курсов, не добавляя EUR автоматически в публичный переключатель валют.

Нельзя считать, что API всегда вернёт THB.

## 13. Переводы

API передаёт RU и EN, но не TH.

Правила первого этапа:

- сохранять `title_ru/en`, `description_ru/en`, `complex_name_ru/en`;
- не копировать русский или английский текст в тайские поля;
- импортированный объект без тайского перевода сначала создавать неактивным;
- тайский перевод выполнять существующим контролируемым механизмом;
- только после проверки разрешать публикацию.

## 14. Slug и защита локальных правок

Slug создаётся только при первом создании `Property` и затем не меняется при изменении названия в API.

API-синхронизация не должна перезаписывать:

- `slug` существующего объекта;
- `custom_title_*`, `custom_description_*`, `custom_keywords_*`;
- `is_featured` и `featured_priority`;
- `contact_person`;
- `views_count`;
- вручную заблокированные поля;
- тайские тексты;
- локальные изображения, не связанные с `ArealistingAsset`.

Уточнение клиента от 2026-09-13: для каждой связи хранится точный список полей,
которыми управляет AREALISTING. Ручное изменение такого поля в стандартной
карточке `Property` автоматически включает его защиту от следующих обновлений.
Для базового RU-поля и его modeltranslation-пары защита включается совместно;
три пересчитанных поля цены также защищаются как единый блок. Защита удобств
включается при ручном изменении inline-характеристик. Возврат поля под управление
источника выполняется только явно — снятием соответствующей галочки в админке
группы публикации.

Карточки, существовавшие в Undersun до связи, не получают полный автоматический
импорт: у них обновляются только поля, явно выбранные при сопоставлении, и цена,
если она не защищена. Полный набор совместимых полей получает только неактивный
черновик, созданный отдельным действием из AREALISTING. Пустое или отсутствующее
значение источника не очищает уже заполненное локальное скалярное поле; `slug`,
TH-переводы, SEO overrides, публикационная активность, приоритет, контакты и
локальные изображения всегда остаются локальными.

## 15. API-клиент

`ArealistingClient` должен:

- использовать `requests.Session`;
- передавать Bearer token в заголовке;
- иметь обязательный timeout;
- предоставлять методы `iter_projects`, `iter_units`, `iter_payment_plans`, `iter_deletions`;
- скрывать пагинацию от sync-сервиса;
- проверять JSON и структуру `data/meta`;
- учитывать `Retry-After` для HTTP 429;
- повторять временные ошибки 5xx и сетевые ошибки с ограниченным exponential backoff;
- не повторять автоматически 400, 401, 403 и 422;
- выбрасывать типизированные исключения без токена и полного заголовка Authorization.

Ориентировочная политика повторов:

- максимум 3 повтора;
- задержки 1, 2 и 4 секунды;
- `Retry-After` имеет приоритет для 429;
- после исчерпания попыток запуск помечается failed.

## 16. Полная синхронизация

Порядок:

1. Зафиксировать `sync_started_at` в UTC.
2. Получить все `/projects` до `has_more=false`.
3. Получить все `/units` до `has_more=false`.
4. Получить все `/payment-plans` до `has_more=false`.
5. Обновить локальные source-модели через `update_or_create`.
6. Пересчитать существующие публикационные группы и подготовить новые группы к ручному подтверждению.
7. Обновить только согласованные поля ранее сопоставленных карточек; не создавать новые `Property` и не включать новые units в группы автоматически.
8. Сравнить полный набор доступных внешних ID с предыдущим набором.
9. Пометить отсутствующие AREALISTING-юниты недоступными и пересчитать группы.
10. После полного успеха сохранить watermark.

Объекты других источников полная сверка не затрагивает.

## 17. Инкрементальная синхронизация

1. Взять `last_successful_sync_at` последнего успешного запуска.
2. Зафиксировать новое `sync_started_at` до первого API-запроса.
3. Передать предыдущий watermark как `updated_since` для projects, units и payment plans.
4. Передать его как `since` для deletions.
5. Повторно обработать данные идемпотентно.
6. Продвинуть watermark до `sync_started_at` только после успеха всех ресурсов.

Параметр API использует сравнение `>=`, поэтому повторное получение записей на границе времени нормально и должно обрабатываться без дублей.

При частичном сбое watermark не продвигается.

## 18. Обработка удалений и недоступных проектов

Для `/deletions`:

- `unit` — пометить `ArealistingUnit` удалённым и пересчитать связанную публикационную группу;
- `project` — пометить проект и его юниты удалёнными, деактивировать связанные публикационные группы;
- `payment_plan` — удалить или пометить удалённой только source-запись;
- не вызывать физический `delete()` для `Property` и `PropertyImage` без отдельного решения.

Если после SOLD/deletion в публикационной группе не осталось доступных units, соответствующий `Property` обрабатывается по согласованной sold-page policy.

Так как project deselection не возвращается `/deletions`, минимум раз в сутки или неделю должна выполняться полная reconciliation-синхронизация.

## 20. Транзакции, идемпотентность и блокировка запуска

- Повторный запуск с теми же данными не создаёт новые `Property`, features или images.
- Уникальность определяется по `external_id`.
- Использовать короткие `transaction.atomic()` на сущность или страницу, а не одну транзакцию на весь feed.
- Запрещать два одновременных запуска через блокировку `ArealistingSyncState` или PostgreSQL advisory lock.
- Курсор считается временным состоянием конкретного прохода; основной checkpoint — последний полностью успешный timestamp.
- Не продвигать checkpoint после частичного успеха.

## 21. Management command

Целевая команда:

```bash
python manage.py sync_arealisting
```

Аргументы:

```text
--full             полная синхронизация и reconciliation
--dry-run          запросить и проверить данные без записи
--since ISO_TIME   вручную задать нижнюю границу delta-sync
--limit N          переопределить page size, максимум 500
--ids ID1,ID2      синхронизировать выбранные external_id
--project-ids ...  ограничить юниты и планы выбранными проектами
--skip-images      не скачивать изображения
--publish          разрешить публикацию валидных новых объектов
--retry-images     повторить неудачные загрузки изображений
```

Примеры безопасного запуска:

```bash
# Проверить авторизацию и схему без записи
python manage.py sync_arealisting --dry-run --limit 1

# Проверить полный feed без записи
python manage.py sync_arealisting --dry-run --full

# Первая загрузка в staging-состояние
python manage.py sync_arealisting --full

# Обычный delta-sync
python manage.py sync_arealisting
```

`--dry-run` не должен создавать SyncState, source-модели, `Property`, файлы или директории media.

## 22. Логи и отчёт запуска

Команда должна выводить агрегированный итог:

```text
Projects: created=0 updated=0 skipped=0 errors=0
Units: created=0 updated=0 mapped=0 skipped=0 errors=0
Properties: created=0 updated=0 deactivated=0
Images: downloaded=0 skipped=0 errors=0
Payment plans: created=0 updated=0 errors=0
Sync status: success|failed|dry-run
```

Не выводить полные payload, Authorization header и API key. Для ошибок допустимы endpoint, HTTP status, `external_id` и безопасный `error.code`.

## 23. Планировщик

Celery в текущем проекте не используется. На production используются management commands из systemd timers:

- `undersun-exchange-rates.timer` — ежедневно в 00:00 `Asia/Bangkok`, запускает `python manage.py update_exchange_rates`;
- `arealisting-prices.timer` — ежедневно в 00:30 `Asia/Bangkok`, запускает `python manage.py update_arealisting_prices`;
- для обоих timers включён `Persistent=true`, поэтому пропущенный из-за остановки сервера запуск выполняется после его включения;
- service-файлы работают от пользователя `ubuntu` из `/home/ubuntu/undersun` через `/home/ubuntu/venv/bin/python`;
- журналы доступны через `journalctl -u undersun-exchange-rates.service` и `journalctl -u arealisting-prices.service`.

`update_arealisting_prices` выбирает только проекты с подтверждёнными связями, для каждого получает полный inventory без скачивания assets и затем пересчитывает цены связанных карточек. Ошибка одного проекта не останавливает обработку остальных, но команда завершается с ненулевым кодом. Глобальная sync-блокировка предотвращает параллельный запуск ручной и плановой синхронизации.

Дальнейшие задачи планировщика: алерт при failed run или длительном отсутствии успешной синхронизации и отдельная согласованная периодичность полной reconciliation списка проектов.

## 24. Тестирование

### API client

- корректный Bearer header;
- timeout;
- пагинация по cursor;
- остановка при `has_more=false`;
- 400/401/403/422 без бесконечных повторов;
- 429 с `Retry-After`;
- ограниченные повторы 5xx;
- невалидный JSON и неправильная схема ответа;
- отсутствие ключа.

### Mapper

- каждый тип недвижимости;
- каждый статус строительства;
- AVAILABLE и SOLD;
- PROJECT/LAYOUT/UNIT grouping;
- несколько units в одной публикационной группе;
- отсутствие AVAILABLE units в группе;
- THB/USD/RUB/EUR;
- отсутствующие nullable-поля;
- неизвестный район;
- существующий Developer и PropertyFeature;
- slug остаётся неизменным при обновлении;
- locked fields не перезаписываются;
- тайские поля не затираются.

### Sync

- повторная синхронизация не создаёт дублей;
- delta обновляет только изменившиеся записи;
- deletion деактивирует только связанный AREALISTING-объект;
- project deletion деактивирует дочерние объекты;
- полная reconciliation обрабатывает deselection;
- watermark меняется только после полного успеха;
- параллельный запуск отклоняется;
- `--dry-run` не меняет БД и storage;
- ошибка изображения не отменяет сохранение валидного объекта.

Тесты не должны обращаться к реальному API и использовать реальный ключ. Ответы API необходимо мокировать.

Этот mapping является рабочей гипотезой, а не подтверждённым контрактом API. Нельзя использовать эмодзи или имя из источника для автоматического изменения существующего локального District.

### 31.2 Проверенные units

Для проекта Lavisco Living получена первая страница из пяти units `705–709`:

- `project_id` совпадает с `project.external_id`;
- unit имеет отдельный `external_id` и `unit_number`;
- присутствуют bedrooms, floor, area, price, currency и price per sqm;
- все пять записей имеют `availability_status=SOLD`;
- `bathrooms=null`;
- `plot_size_sqm=null`, что нормально для CONDO;
- `furnishing=[]` и это нельзя автоматически трактовать как «без мебели»;
- `maintenance_fee` и `sinking_fund` равны `null`, хотя mode заполнен;
- `unit.gallery` содержит по одному изображению планировки;
- `has_more=true`, поэтому первая страница не доказывает отсутствие AVAILABLE units в проекте.

В проверенной выборке `price` точно соответствует `internal_area_sqm * price_per_sqm`. Это наблюдение одного проекта, а не универсальное правило для самостоятельного пересчёта цены.

### 31.3 Выводы для реализации

- Нельзя публиковать только первую страницу; client обязан пройти cursor до `has_more=false`.
- Нельзя считать весь проект проданным на основании пяти первых SOLD units.
- SOLD units сохраняются как source data, но не создают новые активные карточки.
- Каждый unit нужно хранить отдельно для точного обновления цены и статуса.
- Публичная карточка может объединять несколько units, поэтому связь unit → Property не должна быть OneToOne.
- Нельзя группировать планировки только по имени файла `4A`, `4B`, `1A`: нужен стабильный layout ID или ручное подтверждение.
- Project gallery и unit gallery имеют разное назначение и должны храниться раздельно.
- URL assets могут содержать пробелы; downloader должен корректно кодировать URL и не изменять исходный URL, используемый как identity.
- Форматы внешних ID не помещаются в существующее семантическое назначение `legacy_id`; source-модели обязательны.

## 32. Workflow администратора Undersun Estate

### 32.1 Основной принцип

Администратор работает с локальными записями Django Admin и не должен знать:

- endpoint API;
- Bearer token;
- `external_id`;
- `project_id`;
- cursor;
- `updated_since`;
- порядок сетевых запросов.

API-клиент и sync-service формируют запросы автоматически. External IDs показываются только как readonly техническая информация для диагностики.

### 32.2 Разделы Django Admin

В главном меню админки показывается только один пункт интеграции — список проектов AREALISTING. Он служит общей точкой входа: получение данных и переход к сопоставлению. Юниты, группы, локации, материалы, планы оплаты и история доступны внутри через сворачиваемый блок «Настройки и данные интеграции», с учётом прав пользователя. Следующая схема описывает внутренние разделы, а не отдельные пункты главного меню.

```text
AREALISTING
|- Сопоставление с AREALISTING
|- Проекты
|- Юниты
|- Группы публикации
|- Сопоставление локаций
`- История синхронизаций
```

### 32.3 Список проектов

Таблица должна показывать:

| Поле | Пример |
|---|---|
| Проект | Lavisco Living |
| Застройщик | Lavisco |
| География источника | Nai Yang, Sakhu, Thalang |
| Строительство | UNDER_CONSTRUCTION |
| Доступные/проданные units | рассчитывается локально после полного обхода |
| Location mapping | Готов / Требуется настройка |
| Последняя синхронизация | дата и время |
| Состояние импорта | Не импортирован / Черновик / Опубликован / Ошибка |

Поиск по названию проекта, developer и локации работает по локальной БД. API `1.1.0` не предоставляет документированный текстовый поиск проектов.

Действия:

- `Обновить список проектов`;
- `Синхронизировать юниты выбранных проектов`;
- `Сопоставить с существующей карточкой Undersun`;
- `Посмотреть и применить обогащение выбранных полей`;
- `Создать/обновить группы публикации`;
- `Создать черновики Property`;
- `Повторить загрузку assets`.

### 32.4 Карточка проекта

Администратор видит:

- RU/EN описание, developer, тип и статус строительства;
- ownership, fees и дату завершения;
- координаты и source locations;
- project gallery и документы;
- полное количество AVAILABLE/SOLD units;
- диапазоны цен, площадей и спален;
- предупреждения о missing mapping, переводах и данных;
- историю последних sync runs.

Кнопка `Синхронизировать юниты` внутри сама выполняет все cursor-запросы с нужным `project_id`.

### 32.5 Сопоставление локаций

Если source location неизвестна, администратор один раз выбирает:

```text
AREALISTING: Amphoe Thalang -> DISTRICT -> Undersun: Thalang
AREALISTING: Nai Yang       -> LOCATION -> Undersun: Nai Yang
AREALISTING: Sakhu          -> IGNORE
```

После сохранения mapping все новые проекты с теми же external IDs распределяются автоматически. Объект с неподтверждённой обязательной географией остаётся source-записью и не публикуется.

### 32.6 Группы публикации

После загрузки всех units администратор выбирает продуктовый режим:

- `PROJECT` — одна карточка проекта со всем доступным inventory;
- `LAYOUT` — отдельная карточка каждой подтверждённой планировки;
- `UNIT` — отдельная карточка физического unit.

До получения `layout_id` автоматическая LAYOUT-группировка должна требовать ручного подтверждения. SOLD units видны в source inventory, но по умолчанию не предлагаются для создания активной группы.

Для каждой группы показываются:

```text
Название
Количество доступных units
Диапазон площадей
Диапазон цен
Спальни
Основная gallery
Floorplans
Предупреждения
```

### 32.7 Публикация

Workflow:

1. Планировщик или администратор обновляет локальный source feed.
2. Система считает AVAILABLE/SOLD и показывает изменения.
3. На общем экране сопоставления администратор выбирает комплекс, проверяет предложенные соответствия существующим карточкам Undersun и пакетно подтверждает выбранные связи; неподтверждённые кандидаты остаются только в source inventory.
4. Администратор выбирает общие поля для обогащения выбранных карточек, проверяет предварительные изменения и при необходимости задаёт индивидуальные исключения. Географический mapping проверяется перед изменением географии.
5. Система применяет подтверждённые изменения к существующему `Property`, сохраняя его ID, slug и защищённые локальные поля.
6. Если подходящей карточки нет, администратор отдельным действием создаёт неактивный `Property`-черновик из выбранного предложения.
7. Редактор проверяет новый черновик: заголовок, тексты, цену, изображения, географию и TH-перевод; пользователь с правом публикации отдельно публикует карточку.
8. Последующие обновления цены применяются только к подтверждённым связям: на production ежедневно в 00:30 загружается актуальный inventory связанных проектов и пересчитывается цена продажи. Статусы `Property` автоматически не меняются. Перенос пяти поддерживаемых характеристик требует подтверждения администратора (раздел 1.2). Новые units автоматически не включаются в публичное предложение.

### 32.8 Dashboard синхронизации

Администратору нужен короткий итог, а не технический JSON:

```text
Новые проекты: 2
Новые AVAILABLE units: 14
Изменились цены: 5
Стали SOLD: 3
Требуют location mapping: 1
Ошибки assets: 2
Последняя успешная синхронизация: 2026-09-01 10:30 UTC
```

Массовая деактивация, большое уменьшение числа AVAILABLE units и отсутствие успешной синхронизации должны требовать предупреждения или подтверждения согласно согласованной operational policy.

### 32.9 Основной экран массового сопоставления

Исправлено редактирование существующих связей: на экране подбора можно заменить или расширить сохранённый набор предложений (минимум одно). Исключённые units отвязываются, выбранные связываются с прежней группой; сводные характеристики группы пересчитываются. Перед записью проверяется исходный состав на момент открытия страницы, чтобы не перезаписать более поздние изменения другого пользователя. Старое ограничение с переходом в «Группы публикации» для изменения состава снято.

Уточнение после проверки 8 Atelier Residence: кандидаты подбираются при одинаковом количестве спален и разнице площади до 1 м² (Undersun: 51/85/122 м², источник: 51,80/85,35/122,70 м²). Интерфейс объясняет расхождение как возможное округление, но не подтверждает связь автоматически. Доступные предложения показываются первыми; если все близкие варианты SOLD, выводится пояснение. Вкладка без подтверждённых связей называется «Ещё не связаны»: отсутствие связи не доказывает отсутствие соответствующей карточки в Undersun. Это уточняет прежнее название «Нет в Undersun» ниже.

Уточнение интерфейса 2026-09-05: вместо стандартного списка проектов Django реализована рабочая страница с карточками комплексов, поиском, загрузкой предложений выбранного комплекса и переходом к подбору. Пользователь проходит три понятных шага: «Выберите комплекс → Подберите карточки → Проверьте и сохраните». На подборе карточка Undersun с фотографией показана рядом с предложениями источника; выбор предложений включает карточку в пакет без дополнительного чекбокса. Проверка изменений открывается отдельным шагом, после сохранения доступны действия продолжения. Технические разделы остаются второстепенными.

Согласовано 2026-09-05: основной рабочий интерфейс — общий экран «Сопоставление с AREALISTING» внутри Django Admin. Последовательное открытие каждой карточки Undersun не должно быть обязательным: администратор обрабатывает целый комплекс за один проход.

Дополнение 2026-09-07: для обратного сценария добавлен экран «Объекты Undersun без связи». Он начинает работу с конкретной карточки Undersun, позволяет искать проект AREALISTING независимо от различий в написании названия и передаёт выбранную карточку на экран сопоставления. Карточки, для которых интеграция не применяется, отделяются явной отметкой «Ведём вручную». Эта отметка хранится отдельно от `Property`, не влияет на публикацию и автоматически удаляется при создании связи.

Интерфейс предназначен для нетехнического пользователя: понятные названия действий, фотографии, характеристики и объяснения совпадений. Термины `external_id`, source-модель и ListingGroup не требуются для выполнения основных действий.

#### Подбор и подтверждение связей

1. Администратор выбирает комплекс AREALISTING через поиск по названию; результаты показывают фотографию и застройщика.
2. Система подбирает существующие карточки Undersun и предлагает соответствия юнитам выбранного комплекса.
3. Таблица показывает карточку Undersun, предложенный юнит или несколько кандидатов, основные характеристики и понятную причину совпадения либо неоднозначности.
4. Администратор отмечает подходящие строки и подтверждает выбранные связи одним действием.
5. Неоднозначные соответствия раскрываются прямо на этом экране: фотографии, номер юнита, спальни, площадь, этаж, цена и доступность. Можно исправить предложение системы или оставить карточку без связи.

Пример представления:

| Карточка Undersun | Предложение AREALISTING | Результат сравнения |
|---|---|---|
| Квартира 45 м², 1 спальня | Юнит A305, 45 м² | Совпадают площадь и спальни |
| Квартира 62 м², 2 спальни | Юниты B201, B301 | Нужно выбрать |
| Вилла с бассейном | Нет кандидатов | Оставить без связи |

Совпадение названия комплекса, площади или количества спален используется только для подбора кандидатов и не доказывает идентичность физического объекта. Автоматическое предложение не является подтверждённой связью. Для карточки, представляющей несколько units, администратор явно подтверждает их состав; привязка комплекса не включает все его units автоматически.

#### Пакетное обогащение

- Администратор один раз выбирает поля для обновления у отмеченных карточек.
- До применения экран показывает сравнение «Сейчас в Undersun → Данные AREALISTING» по каждой карточке.
- Можно исключить отдельную карточку или поле из пакетного изменения; индивидуальные настройки и защищённые поля сохраняются.
- Подтверждение связи и применение обогащения — различимые действия: сохранение связи само по себе не разрешает перезапись всех данных.
- Применение сохраняет существующие ID, URL и локальные настройки карточек согласно правилам владения полями.

#### Активность карточки Undersun и доступность AREALISTING

На экране сопоставления необходимо явно разделять два независимых состояния:

- `Property.is_active` — показывается ли карточка Undersun на публичном сайте;
- `ArealistingUnit.availability_status` — доступно или продано конкретное предложение источника.

`Property.status` не изменяется в рамках этого сценария: уточнение клиента относится именно к видимости карточки через `is_active`. Автоматическая установка локального статуса `sold` остаётся отдельным продуктовым решением.

| Карточка Undersun | Связанные или выбранные units AREALISTING | Поведение интерфейса |
|---|---|---|
| Активна | Есть AVAILABLE | Показать нормальное состояние без предупреждения |
| Активна | Все SOLD | Показать заметное предупреждение и предложить снять активность |
| Неактивна | Есть AVAILABLE | Показать, что предложения доступны, но карточка скрыта с сайта |
| Неактивна | Все SOLD | Показать состояние без требования действия |

Правила реализации:

- на каждой карточке Undersun показывается понятный статус «Активна на сайте» или «Неактивна» и элемент ручного изменения `is_active`;
- вывод о доступности строится только по units, уже связанным с этой карточкой либо выбранным для неё в текущем подтверждаемом наборе; SOLD других планировок и units комплекса не должен влиять на карточку;
- если все такие units имеют статус SOLD, а `Property.is_active=True`, интерфейс предупреждает: «Все связанные предложения проданы, но карточка Undersun активна»;
- изменение активности не применяется немедленно: оно включается в финальное сравнение, например «Активность: активна → неактивна», и сохраняется только после подтверждения;
- сохранение выполняется транзакционно вместе с выбранными связями и остальными подтверждёнными изменениями, проверяет актуальное значение после открытия экрана и записывается в историю Django Admin;
- source-sync не переключает `Property.is_active` автоматически. Даже при всех SOLD решение о деактивации принимает пользователь с правом изменения карточки;
- обратное включение карточки также является явной публикационной операцией и не должно происходить вследствие появления нового AVAILABLE unit.

#### Предложения без соответствий

Вкладка «Ещё не связаны» на экране выбранного проекта показывает units без подтверждённого соответствия. Отсутствие связи ещё не доказывает, что соответствующей карточки нет на сайте: сначала администратор должен иметь возможность найти её и связать. Units без подтверждённой связи не участвуют в публичной выдаче, фильтрах, счётчиках, диапазонах цен, карте и sitemap.

Если после проверки карточки Undersun действительно нет, предлагается следующий сценарий:

1. Администратор выбирает один или несколько units, которые должны представлять одну новую карточку.
2. Нажимает отдельное действие «Создать карточку Undersun».
3. Система показывает предварительный просмотр переносимых данных и предупреждения о недостающем mapping.
4. Создаётся связанный `Property` с `is_active=False`; обычное получение feed никогда не выполняет это действие автоматически.
5. После создания открывается стандартная карточка Django Admin, где редактор проверяет и дополняет данные.
6. Публикация выполняется отдельно пользователем с соответствующим правом.

В черновик переносятся все однозначно и безопасно сопоставимые поля: заголовок и
описание RU/EN, название комплекса, тип и стадия готовности, подтверждённая
география и координаты, застройщик, спальни, целое количество ванных, этаж,
общая площадь и площадь участка, год завершённого проекта, меблировка, основные
флаги удобств, список `PropertyFeature`, вид на море и минимальная цена среди
выбранных AVAILABLE units. Если у выбранных units нет единого значения
обязательной характеристики либо отсутствует обязательный
`PropertyType`/`LocationMapping`, система должна остановить создание и показать,
что требуется настроить. Thai-контент, SEO overrides, публикационные настройки,
контакты и локальная галерея автоматически не заполняются.

Если все выбранные units уже SOLD, по умолчанию новый черновик не создаётся. Администратору показывается объяснение и отдельное сохраняемое действие «Пропустить», чтобы предложение не оставалось постоянной задачей в очереди. Это решение относится только к созданию новой карточки и не заменяет политику обработки уже существующих публичных страниц.

Новые юниты уже связанного комплекса после очередной синхронизации также требуют явного выбора администратора перед включением в публичное предложение.

#### Роль карточки объекта и выбор технологии

В существующей карточке Undersun достаточно показывать краткую информацию о связи, выбранных юнитах, дате обновления и ссылку для редактирования связи. Это дополнительная точка входа, а не обязательный путь массовой работы.

Vue рассматривается как подходящий вариант для интерактивного экрана внутри Django Admin: поиск, таблица сопоставления, выбор юнитов и предварительное сравнение. Использование Vue не является обязательным требованием и не подразумевает перевод всей админки на Vue. Django сохраняет авторизацию, проверку прав и серверную валидацию изменений.

#### Критерии приёмки интерфейса

- Администратор может сопоставить несколько карточек одного комплекса без открытия каждой карточки по отдельности.
- Предложенные совпадения имеют объяснения, а неоднозначные варианты можно проверить и исправить на том же экране.
- Выбранные связи подтверждаются пакетно; изменения данных видны до применения и допускают индивидуальные исключения.
- Для каждой карточки видна её текущая активность в Undersun и доступность выбранных units AREALISTING; конфликт «активна, но все предложения SOLD» выделен явно.
- Ручное изменение `Property.is_active` видно на экране проверки и не выполняется автоматически source-sync.
- Несопоставленные и вновь полученные юниты не изменяют публичный каталог без отдельного выбора администратора.
- Создание новых карточек явно отделено от обогащения существующих, создаёт только неактивный черновик и не происходит при обычном получении данных.
- Предложение, по которому карточка не нужна, можно явно пропустить, не удаляя source data.

#### Оптимизация фотографий и планировок в предпросмотре (2026-09-14)

- Блок «Фотографии и планировки из AREALISTING» закрыт по умолчанию, поэтому при открытии предпросмотра браузер не загружает исходные изображения.
- После раскрытия блока загружаются первые 4 изображения каждой секции; остальные показываются и загружаются порциями по 4 по кнопке «Показать ещё».
- До фактического показа у изображения отсутствует `src`: одного `loading="lazy"` недостаточно, чтобы гарантированно исключить сетевую загрузку скрытых карточек.
- Все доступные изображения по-прежнему выбраны для импорта по умолчанию, включая ещё не показанные. Оптимизация не меняет правила выбора и серверного импорта медиа.
